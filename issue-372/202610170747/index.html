#372 The product-picker widget's CSP allows data: and the ChatGPT copy declares no MCP Apps CSP

ready for human review

The product-picker widget's Content Security Policy (CSP, the browser rules on what a widget may load) lists the bare scheme `data:` in both widget registrations, and the ChatGPT (skybridge) copy only has `openai/widgetCSP`, with no `_meta.ui.csp`. After the fix, both registrations declare the same specific-origin-only policy (image domains plus the server origin), no `data:`. Hosts that read `_meta.ui.csp` get the same policy as ChatGPT. The inline SVG placeholder still renders, because the MCP Apps default CSP already allows `img-src data:`.

What changed

The product-picker widget is served twice, once for MCP Apps hosts like Claude and once for ChatGPT (the "skybridge" copy). Each copy declares a Content Security Policy (CSP), the browser rules for what the widget may load. Both copies listed the bare scheme `data:`, which the Is Agentic `mcp-view-csp` check refuses. The ChatGPT copy also declared its policy only in ChatGPT's own format (`openai/widgetCSP`). An MCP Apps host reading that copy found no `_meta.ui.csp` and fell back to its restrictive default. What changed in `packages/credentagent-storefront/src/server.ts`: - `data:` is removed from both registrations. Product images and the FR-014 placeholder are inline `data:image/svg+xml` URIs. They don't need a declared entry, because the MCP Apps default view CSP already includes `img-src 'self' data:`. The comments that said `data:` was needed are corrected. - The skybridge copy now declares `_meta.ui.csp` (`resourceDomains`: the picsum image origins; `connectDomains`: the server origin) alongside its existing `openai/widgetCSP`, so both kinds of host get the same policy. Test: a new block in `server.test.ts` reads both widget resources over the MCP client. For each, it checks that `_meta.ui.csp` is present with exactly the image origins and the server origin. For the skybridge copy, it checks that `openai/widgetCSP` matches. It also checks that no entry is a bare scheme (`data:`, `https:`, …) or `*`. I ran it on the old code before the fix and it failed on the `data:` entry. It also fails if the skybridge `_meta.ui.csp` is removed, because its first assertion is that the policy exists. Verification: `npm run build`, `typecheck`, `lint` and the root `npm test` all pass (84 files, 1364 tests). Not verified here: these need a real host and must be checked by hand after merge. - That images still render in Claude and ChatGPT. The ChatGPT default for `data:` images in particular is an assumption. - The Is Agentic re-scan. The issue contained no instructions to change tools, CI or process.

Files: packages/credentagent-storefront/src/server.test.ts, packages/credentagent-storefront/src/server.ts

What the recordings show

The storefront MCP server ran from each checkout (`node examples/storefront.mjs`, ports 4320/4321), and the script sent the same JSON-RPC calls to both: initialize, then resources/list, then resources/read for both product-picker URIs. Each live response is shown as a rendered page. BEFORE (main): the MCP Apps registration's `_meta.ui.csp.resourceDomains` contains the bare scheme "data:". The skybridge registration has no `_meta.ui.csp` at all, only `openai/widgetCSP`, whose `resource_domains` also contains "data:". AFTER (fix): both registrations declare `_meta.ui.csp` with `resourceDomains` = [https://picsum.photos, https://fastly.picsum.photos] and `connectDomains` = [server origin]. The skybridge item keeps `openai/widgetCSP` with the same lists. The script's own check for a bare scheme or wildcard finds none in any list. A further after-only capture renders an exact copy of the FR-014 `placeholderDataUri()` SVG on a page whose CSP is the MCP Apps default `img-src 'self' data:` plus the fixed resourceDomains. The placeholder loads at 400x300, so removing `data:` from resourceDomains does not break it when the host default allows `data:` images.

Limits: These captures show the server's declared CSP metadata. They do not show the widget running inside a real host. Claude and ChatGPT were not available, so whether product images render in the product-picker in those hosts, and whether the is-agentic re-scan now passes `mcp-view-csp`, must be checked by hand after merge. The placeholder page builds its CSP by hand on the assumption that hosts apply the MCP Apps default `img-src 'self' data:`; it does not prove any particular host does so. It also uses a copy of `placeholderDataUri()`, not the built widget bundle. The "non-allowlisted image blocked" result may partly reflect the sandbox having no outbound network, so it is not strong proof that the CSP blocks it. The issue contained no embedded instructions to change tools, credentials, CI or process.
