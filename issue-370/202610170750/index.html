#370 Router: return Markdown from credentagent.ai/ when an agent asks for it (Accept: text/markdown + Vary: Accept)

ready for human review

Today credentagent.ai/ always returns the HTML product page, even when an AI agent asks for Markdown. The change adds a router rule: a request to `/` with an `Accept` header containing `text/markdown` is forwarded to `https://openmobilehub.org/credentagent/index.md`. It answers with `Content-Type: text/markdown; charset=utf-8`. `/` gets `Vary: Accept, Accept-Encoding` so a CDN cannot serve the Markdown copy to browsers or the reverse. Browsers and `Accept: text/html` still get the HTML page. The change is config only (`deploy/router/vercel.json`), plus a config test and a README note. The `index.md` file itself comes from openmobilehub/credentagent-website#33 in another repo; until that is live the Markdown rewrite will return the upstream's error. That is outside this repo's code, so I note it as a deploy-order caveat and not a blocker.

What changed

credentagent.ai/ now answers in Markdown when an AI agent asks for Markdown. Before this change it always sent the HTML product page. What changed, all in `deploy/router/`: - `vercel.json`: a new rewrite rule. A request for `/` whose `Accept` header contains `text/markdown` is forwarded to `https://openmobilehub.org/credentagent/index.md`. The rule sits before the existing `/` rule, which still sends everyone else to the HTML page and is unchanged. Two new `headers` entries for `/`: every response gets `Vary: Accept, Accept-Encoding`, so a cache can't hand the Markdown copy to a browser or the reverse. Only Markdown requests get `Content-Type: text/markdown; charset=utf-8`, so the HTML response keeps its own type. The `/marketplace/*`, `/marketplace-dev/*` and `/api/ask` routes are untouched. - `config.test.mjs` (new; the root `npm test` runs it): reads `vercel.json` and works out the result the way Vercel does. The first matching rewrite wins, every matching `headers` entry applies, and a `has` value is a regex on the header. It checks what each request gets: `text/markdown`, a mixed `text/html;q=0.9, text/markdown`, `text/html`, a browser's `Accept` header, and no `Accept` header at all. It also checks that the Markdown rule comes before the HTML one, and that marketplace paths ignore the Markdown header. - `README.md`: describes the behaviour and says it depends on openmobilehub/credentagent-website#33, which publishes `index.md`. It lists the issue's two curl commands to run against the live site after a deploy. Test-first: on main, the new test failed 4 of its 8 cases: both checks that `Vary` includes `Accept` and `Accept-Encoding` (every case), the Markdown destination and type, and the rule order. With the change, all 8 pass. Root checks run separately: `npm run build`, `npm run typecheck` and `npm run lint` all finished. `npm test` passed 85 files and 1374 tests. The issue text had no instructions about tools, credentials, CI or this process.

Files: deploy/router/README.md, deploy/router/config.test.mjs, deploy/router/vercel.json

What the recordings show

I ran the same browser probe against each checkout's deploy/router/vercel.json. A small local stand-in for the Vercel edge (evidence/sim.mjs) resolves requests the way Vercel documents it: rewrites are checked in order and the first match wins, `has` treats the header value as a regex, and every matching `headers` entry is applied. The page sends GET / five times with these Accept headers: text/markdown; text/html; a browser-style header; `text/html;q=0.9, text/markdown`; and no Accept header. On main, all five go to the HTML destination https://openmobilehub.org/credentagent/ and come back with text/html and only `Vary: Accept-Encoding`. That matches the curl output in the issue. With the fix, both requests whose Accept contains text/markdown go to https://openmobilehub.org/credentagent/index.md and come back with `Content-Type: text/markdown; charset=utf-8`. text/html, the browser-style header and no Accept header still get the HTML page with text/html, so the Content-Type override doesn't reach them. All five responses carry `Vary: Accept, Accept-Encoding`. On both sides, a normal Chromium visit to / still shows the HTML page.

Limits: This is not the real Vercel edge. Vercel's rewrites and headers can't run locally, so evidence/sim.mjs reads each checkout's vercel.json and applies Vercel's documented rules for the patterns this file uses: an exact "/" match, ":path*", and header `has` treated as an anchored regex. It shows what the config selects. It does not show Vercel's real behavior, including whether a `headers` Content-Type entry actually overrides the content type an external rewrite returns. The upstream responses are local stubs; nothing was fetched from openmobilehub.org. The HTML stub returns text/html with Vary: Accept-Encoding, as in the issue's curl output. I chose text/plain for the Markdown stub's own content type, which is an arbitrary choice; the fix's header entry replaces it either way. The real Markdown body depends on openmobilehub/credentagent-website#33 publishing index.md, and the live check is still the two curl commands from the issue, run after deploy-prod. I didn't run the repo's config.test.mjs (vitest) for these captures, so its output isn't shown. CDN caching is not exercised; only the presence of the Vary header is. The issue text contained no instructions about tools, credentials, CI or process.
