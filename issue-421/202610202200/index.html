#421 Issue agent's internal reviewers report only what blocks

ready for human review

An internal reviewer marks a comment's wording as blocking, so the agents spend another paid round rewording it. Nothing tells the reviewers which problems may block and which may not. The reviewers get one short list of what blocks: security breaks, missing tests, real bugs, false claims, rubric regressions, oversized changes. Wording and unreachable edge cases are suggestions, shown on the pull request but never sent back.

What changed

The issue agent's three internal reviewers (spec, security, developer experience) now get a fixed list of what may block a merge. The list has six items: a broken security invariant, a missing bypass test for a new or changed control, a correctness bug, a release or README claim the code doesn't back, a regression against the DX rubric, and a change too big or outside its ticket. They are also told what never blocks: comment wording, doc phrasing, and an edge case that needs a host to break its declared types. Before this, "blocking" only meant "a maintainer would request changes", so a wording note could send the work back for another paid round. Changes: - `ci/issue-agent/roles.mjs`: `DEFAULT_REVIEW_RULES` now opens with the blocking and never-blocking lists. The severity sentence in `reviewPrompt` was rewritten and stays in every repo's prompt. It says a finding is "blocking" only in the classes the rules list, and everything else is a "suggestion": reported on the draft pull request, never sent back to the implementer. - `ci/issue-agent/checks.mjs`: a new pure function, `reviewFeedback({ reviews, criteria })`, returns `{ clean, blocking, unmet, feedback }`. Only blocking findings and unmet or missing criterion verdicts go into `feedback`. `run.mjs` now calls it instead of building the feedback inline; the behavior and the log line are the same. - `ci/issue-agent/README.md`: the review step now says that only blocking findings and unmet criteria go back to the implementer. Suggestions are reported on the draft pull request. A repo's own `reviewRules` replaces the default list. Tests were written first and failed 7/7 before the fix. The root `npm run build`, `npm run typecheck`, `npm run lint` and `npm test` all pass: 92 files, 1549 tests. I could not run a manual mutation check, because the sandbox refused the command. By reading the test, it fails if the severity filter is removed: the suggestions-only case would then not be clean. The pipeline runs its own mutation check. No instructions in the issue asked to change tools, CI or the process.
