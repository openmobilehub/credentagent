#343 The consent-page lint rule misses a wrapped JSON.stringify(…)

ready for human review

The lint rule that bans JSON.stringify inside ceremony page templates only matches when the call is a direct child of the template literal, so a wrapped form like ${JSON.stringify(x).replace(...)} slips through. The fix switches the selector in eslint.config.js to the descendant combinator so any JSON.stringify nested inside a template expression is flagged, and updates the REVIEW.md section 0 sentence that lists what lint misses. Nothing a user sees changes; the current tree has one existing direct match (intent-sign/mandates.ts:75) that already carries a justified eslint-disable.

What changed

The lint rule for consent pages now catches `JSON.stringify(…)` anywhere inside a page template expression, including wrapped forms such as `${JSON.stringify(url).replace(…)}`. Before, it only caught a call sitting directly in the template. That gap could have let the issue 330 bug come back: a value holding `</script>` ends the page's script early. Nothing a user sees changes. **Changes** - `eslint.config.js`: in the ceremony `no-restricted-syntax` rule, the selector changed from `TemplateLiteral > CallExpression[…JSON.stringify]` ("direct child") to `TemplateLiteral CallExpression[…JSON.stringify]` ("any descendant"). The comment above it now explains this. The error message, which points to `scriptJson()`, was already accurate for nested calls, so it is unchanged. - `REVIEW.md` §0: no longer lists "a wrapped `JSON.stringify`" as something lint misses. It still lists what lint can't see: a precomputed `JSON.stringify` (assigned to a variable, then interpolated), a raw value in a script, and an unencoded `cart` join. It also notes that a legitimate non-script use needs an `eslint-disable` with a one-line reason. - New `eslint-config.test.ts` at the repo root, so only the root `npm test` runs it. It feeds source text through ESLint with the repo's real config, under a ceremony file path. **Trade-off (from the issue):** the rule now also flags a `JSON.stringify` nested inside other helpers in a template, such as `escapeHtml(JSON.stringify(x))`. The current tree has no such call, and `npm run lint` is clean. **Checks:** `npm run build`, `npm run typecheck`, `npm run lint` and the root `npm test` (87 files, 1388 tests) all pass. The new test failed on the old selector before the fix. Putting the `>` back afterwards makes the wrapped and nested tests fail again. The issue contained no instructions about tools, credentials or CI.
