#322 A store served under a path publishes its signing key where nobody looks for it

ready for human review

Some stores sit under a path, for example `https://shop.example/store/` (version 0.6.0 supports this). On current main such a store gives itself the wrong identity and puts its public signing key where nobody will look. Its identity is a did:web id, a web address-style name that tells others where to download the key. `didWebFor()` (packages/credentagent-gate/src/ap2/keys.ts:67) builds that id from the host alone and drops the path, so the store becomes `did:web:shop.example`. Under the did:web rules, that id points to `https://shop.example/.well-known/did.json`, the site root. Meanwhile `mount()` (client.ts:389) registers only `/.well-known/did.json`, and behind a proxy that strips the path the file ends up at `https://shop.example/store/.well-known/did.json`. Nobody resolving the id would look there. The result: AP2 mandates (the signed spending permissions the gate issues) from a path-mounted store can't be checked by anyone else, and two stores on one host would claim the same identity. After the fix, a path-mounted store's identity includes its path (`did:web:shop.example:store`). That id is used as the mandates' issuer, as the key ids, and as the DID document's id. `mount()` also serves the document at `/did.json`, which the proxy exposes at `https://shop.example/store/did.json`, exactly where did:web resolution looks. A store at the site root is unchanged: it keeps `did:web:shop.example`, keeps `/.well-known/did.json`, and mandates it already signed still verify. The issue's related point about the merchant id was already fixed on main: `merchantFor()` in ap2/from-gate.ts:33-36 now includes the base path (pull request #334, which fixed issue #331), so it is out of scope here.

What changed

**What was wrong.** A store that sits under a path, for example `https://shop.example/store/` (version 0.6.0 supports this), gave itself the wrong identity. The identity is a did:web id: a web-address-style name that tells others where to download the store's public signing key. `didWebFor()` built that id from the host alone, so the store called itself `did:web:shop.example`. Under the did:web rules, that id points to the site root (`https://shop.example/.well-known/did.json`). Meanwhile `mount()` only served `/.well-known/did.json`, which a proxy that strips the path exposes at `https://shop.example/store/.well-known/did.json`. Nobody resolving the id looks there. So nobody outside the store could check the AP2 mandates it signed (the signed spending permissions the gate issues), and two stores on one host would claim the same identity. **What changed.** - `didWebFor()` (packages/credentagent-gate/src/ap2/keys.ts) now follows the did:web path rule. Each path segment becomes its own colon-separated, percent-encoded part. A trailing slash, the query and the fragment are ignored. So `https://shop.example/store` becomes `did:web:shop.example:store`. Segments are decoded and then re-encoded. That way a `:` inside a segment is escaped, and a malformed escape like `%zz` can't throw. - That id is now used everywhere the old one was: as the mandates' issuer (`iss`), in the key ids (`kid`), and as the DID document's `id`. - `mount()` now also serves the DID document at `/did.json`, which the proxy exposes at `https://shop.example/store/did.json`, exactly where did:web resolution looks. It still serves `/.well-known/did.json`. Both routes are registered in `publishSigningKey`. That function already runs first on all three `mount()` paths and only once, because a flag stops a second `mount()` from registering the routes again. - A store at the site root is unchanged: it keeps `did:web:shop.example` at `/.well-known/did.json`, and mandates it already signed still verify. - Docs updated to say where a path-mounted store's DID and document live: the comments in keys.ts, client.ts and types.ts, and the AP2 section of the gate README. The README says plainly that a published key is not issuer-verified trust. - Out of scope: the issue's related point about two path-mounted stores sharing a merchant id. That was already fixed on main by pull request #334 (issue #331). **Checks.** Run from the repo root, all passed: `npm run build`, `npm run typecheck`, `npm run lint` and `npm test` (81 test files, 1229 tests, including the cross-package file). Before the fix, the new tests failed on main: `GET /did.json` returned 404, and the mandate's `iss` was `did:web:shop.example`. That failing run had both fixes missing at once. I did not separately re-run with only one of the two fixes put back.

What the recordings show

Each side runs the same input. A real Express app hosts `new CredentAgent({ walletOrigin: "https://shop.example/store" })` and `mount(app)`, served under `/store` through `outer.use("/store", app)`, which strips the prefix the way a path-stripping proxy does. localhost:4320–4323 stands in for https://shop.example. BEFORE (main): `/store/did.json` is a 404 ("Cannot GET /store/did.json"). The key does sit at `/store/.well-known/did.json`, but its document id is `did:web:shop.example`. A resolver page applies the did:web rules to the id the store claims. It maps `did:web:shop.example` to https://shop.example/.well-known/did.json, gets a 404 and shows FAIL, so nobody can find the store's key. AFTER (fix): `/store/did.json` returns 200 with id `did:web:shop.example:store`. Both verificationMethod ids are under that DID (`#gate-signing-key` first, then `#merchant-checkout-key`), and so are the controllers. Resolving `did:web:shop.example:store` maps to https://shop.example/store/did.json, returns the identical document, and shows PASS. Control: a root store (`walletOrigin: "https://shop.example"`, mounted at the root) serves `/.well-known/did.json` with id `did:web:shop.example`, and resolution passes on both sides. After the fix the root store also serves the same document at `/did.json`.

Limits: The captures show what the store serves at each URL and where did:web resolution leads. Several things they don't show: (1) No real reverse proxy or real shop.example domain is involved. Express `app.use("/store", ...)` does the prefix stripping, and the resolver page swaps https://shop.example for http://localhost:PORT. (2) The resolver is a small did:web lookup written in evidence/server.mjs, not a third-party DID resolver library. (3) No AP2 mandate is issued or checked in the browser (AC3: `iss`/`kid`, then `publicJwkFromDidDocument` and `verifyMandate`). The captures only show that the published key document can be found and carries the right ids; checking a signature against it is left to the unit tests. (4) Only the legacy `mount(app)` path with no settings is exercised. The explicit ceremony settings and composed-host paths from AC5, and the "a second mount() doesn't register the routes again" behaviour, are not shown. (5) Docs (AC6) and `didWebFor` edge cases such as multiple path segments, a query or a trailing slash (AC1) are not covered. (6) Signing keys are generated fresh on each run, so key material differs between screenshots; only the ids matter.
