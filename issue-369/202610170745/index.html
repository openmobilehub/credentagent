#369 Router: serve every website path at credentagent.ai, not just /

ready for human review

credentagent.ai only forwards "/" to the Pages site; every other path (robots.txt, llms.txt, sitemap.xml, about, contact, privacy) returns a Vercel 404. The fix adds one catch-all rewrite to deploy/router/vercel.json, placed after the /marketplace-dev and /marketplace rewrites, so any path not handled by the router is served from https://openmobilehub.org/credentagent/. /api/ask (a Vercel function) and the marketplace routes keep working. Live checks (200 on llms.txt) depend on the website PR landing and a deploy, so they are post-merge verification.

What changed

**Not checked live: this pipeline cannot deploy the router, so none of the credentagent.ai checks below have been run.** The evidence in this PR is the config change and the test output. A maintainer needs to run the curl checks after the merge triggers the deploy-prod workflow. credentagent.ai only forwarded "/" to the website on GitHub Pages (https://openmobilehub.org/credentagent/). Every other address, such as robots.txt, llms.txt, sitemap.xml or /about, got Vercel's own 79-byte "not found" page, even when the file exists on Pages. This change adds one catch-all rewrite as the last rule in deploy/router/vercel.json: { "source": "/:path*", "destination": "https://openmobilehub.org/credentagent/:path*" }. Any path that no earlier rule claims now passes through to the same path on Pages. Vercel uses the first rewrite that matches, so the catch-all goes after /marketplace-dev/:path* and /marketplace/:path*. Those keep going to their demo deployments. /api/ask is a Vercel function, and Vercel resolves the filesystem and functions before any rewrite, so the catch-all doesn't capture it. deploy/router/README.md now has: - a table row for the catch-all - a paragraph on why its position matters, why /api/ask is unaffected, and that Pages' status codes and content types come through unchanged - curl checks to run by hand after a deploy --- **Checks to run after merge** (each is in the README): - `curl -sI https://credentagent.ai/robots.txt` → 200, text/plain - `curl -sI https://credentagent.ai/llms.txt` → 200, text/plain. This file only exists once credentagent-website#34 lands. - `curl -sI https://credentagent.ai/sitemap.xml` → 200, application/xml - `curl -sI https://credentagent.ai/no-such-page` → 404 from Pages, not Vercel's 79-byte text/plain 404 - `POST /api/ask` and `POST /marketplace/mcp` answer as before **What was verified in the pipeline:** new test deploy/router/vercel-config.test.mjs, which the root `npm test` picks up, pins: - the catch-all is present and is the last rule - the marketplace rules come before it, with their destinations unchanged - the "/" rule is still there - api/ask.mjs is still declared as a function, and no rule before the catch-all matches /api/ask Before the fix, 3 of the 4 tests failed on main. After the fix all 4 pass. As a mutation check, I moved the catch-all to the top of the list by hand, and the ordering and last-rule tests failed; then I put it back. `npm run build`, `npm run typecheck`, `npm run lint` and the root `npm test` (85 files, 1367 tests) all pass. What the recordings show

I ran the same request set through each checkout's actual deploy/router/vercel.json, on main and on the fix. The paths were /, /robots.txt, /llms.txt, /sitemap.xml, /about, /no-such-page, /api/ask, /marketplace/mcp and /marketplace-dev/mcp. A local emulator of Vercel's routing order handles each request: functions resolve first, then rewrites in order with first match winning, and anything unmatched gets Vercel's 79-byte text/plain NOT_FOUND. On main (before), only "/" reaches Pages. robots.txt, llms.txt, sitemap.xml, /about and /no-such-page all fall through to the 79-byte text/plain Vercel 404. On the fix (after), the new last rule /:path* → https://openmobilehub.org/credentagent/:path* sends those paths to Pages. robots.txt and llms.txt return 200 text/plain, sitemap.xml returns 200 application/xml and /about returns 200 HTML. /no-such-page now returns Pages' own 404 (text/html), not the Vercel one. /api/ask still resolves to the function, and /marketplace/mcp and /marketplace-dev/mcp still proxy to their demo deployments, because the catch-all comes after them. Each side has a summary table, which also prints that side's rewrites array, followed by the individual responses opened in the browser.

Limits: None of this ran against the live credentagent.ai, because the pipeline cannot deploy the Vercel router. What these captures show is a local emulator in evidence.mjs. It reads the real vercel.json from each checkout and applies Vercel's documented order: functions resolve before rewrites, the first matching rewrite wins, and `:path*` matches zero or more path segments. It does not simulate Vercel's static-filesystem serving of outputDirectory "." (for example, README.md would be served as a static file on real Vercel). The upstreams are local mocks. Pages is a fake openmobilehub.org/credentagent/ that serves robots.txt, llms.txt, sitemap.xml and /about. Real llms.txt and sitemap.xml depend on the credentagent-website PRs (#34 and others) landing. /api/ask is a stub, not the real handler, so these captures show only which route resolves each path, not what /api/ask returns. Status and content-type pass-through comes from the emulator's own proxy and does not prove that Vercel's external rewrite preserves them. That has to be confirmed after merge with the curl checks in the README, for example `curl -sI https://credentagent.ai/llms.txt`. I did not run the vitest file (vercel-config.test.mjs).
